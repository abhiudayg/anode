# Steady state, n=3, local VM (2026-11-18)

Question from the trust list: is "no measurable latency from orchestration" true, with n≥3 and a direct-port control?

Setup: OrbStack Ubuntu 26.04 arm64 VM (local, not GCE). The same `orders` binary runs in two units: the anode unit (`DynamicUser`, sandboxing; `units/bench-anode.unit`, generated by the real template) and a bare unit (`units/bench-bare.unit`). Caddy fronts each unit on its own port. Route: `GET /healthz`, which is static and does not touch a database. The earlier GCE steady-state run used `GET /v1/orders/{id}` with Postgres; this run does not.

Load: open-loop generator (`steady-state/scripts/loadgen_open.go`), 10 s warm-up, 60 s measured, 256 max in flight, run from the Mac over `orb.local`. Each repetition rotates the arm order.

Arms:
- `direct`: loadgen → service port, no Caddy.
- `anode`: loadgen → Caddy → anode unit.
- `bare`: loadgen → Caddy → bare unit.

Results (`summary.txt`, per-run files in `results/`). Median of 3 runs, with the range in brackets:

| Rate | Arm | p50 ms | p99 ms | p999 ms | Errors |
|---|---|---|---|---|---|
| 100 | direct | 0.68 [0.66–0.70] | 11.1 [9.8–18.9] | 58 [46–68] | 0 |
| 100 | anode | 1.48 [1.35–1.65] | 9.2 [5.3–22.1] | 69 [16–101] | 0 |
| 100 | bare | 1.27 [1.27–1.45] | 33.9 [5.3–53.6] | 244 [15–471] | 0 |
| 500 | direct | 0.43 [0.33–0.48] | 7.1 [3.3–9.3] | 61 [15–67] | 0 |
| 500 | anode | 0.80 [0.77–1.07] | 25.7 [10.7–38.8] | 162 [34–205] | 0 |
| 500 | bare | 0.72 [0.65–1.05] | 15.0 [11.4–18.1] | 66 [32–97] | 0 |

What the data supports:
- Caddy adds a measurable hop. At p50 it is about 0.5–0.8 ms in this setup, and it is the same for both proxied arms. This is the largest difference in the run.
- anode unit vs bare unit: p50 is within about 0.1–0.2 ms, and the ranges overlap. The tail (p99, p999) moves between runs by more than the gap between the arms. Treat anode-vs-bare as no difference that this run can detect, not as a proven zero.
- The run does not show a latency cost from the anode unit at these rates.

What it does not show:
- Tail latency. p999 ranges span up to 5× within a single arm (for example bare at 100 RPS, 15–471 ms). Three runs cannot separate the arms at the tail.
- Database routes. `/healthz` does not query a store. Latency for DB-backed routes is not measured here.
- A remote host. This is a local VM, with the load generator on the Mac.
- Load-path ceiling. The earlier GCE run hit a ~920 RPS ceiling at its 1,000 RPS target; this run stops at 500.

Reproduce (Linux arm64 `orders` binary; loadgen built from `steady-state/scripts`):
```
BIN=./orders-linux-arm64 scripts/bench-setup.sh   # run as root in the VM
LOADGEN=./loadgen_open scripts/bench-run.sh results/   # run on the Mac
python3 scripts/summarize.py results/
```
