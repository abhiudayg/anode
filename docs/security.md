# Security Architecture & Hardening

Anode is built around a zero-trust, least-privilege security model designed for bare-metal Linux servers and Virtual Private Servers (VPS).

---

## 1. Threat Model & Design Principles

| Threat Vector | Traditional Container Orchestrator Risk | Anode Defense-in-Depth |
| :--- | :--- | :--- |
| **Root Escalation** | Containers run with root daemon sockets (`/var/run/docker.sock`). | Unprivileged `anode` user; `NoNewPrivileges=true`; zero docker daemon socket access. |
| **Filesystem Tampering** | Compromised microservice modifies `/etc` or reads other services. | `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`. |
| **Stateful DB Destruction** | Memory leak in microservice triggers Linux OOM killer against DB. | Kernel `OOMScoreAdjust=-900` on databases; `+500` on applications. |
| **Public Database Exposure** | Ports 5432/6379 accidentally mapped to `0.0.0.0`. | Enforced loopback binding (`127.0.0.1`) and nftables zero-trust packet filter. |
| **In-Flight Data Sniffing** | Unencrypted HTTP between edge and internal services. | Automatic Let's Encrypt TLS 1.3 edge termination via Caddy. |

---

## 2. The 6-Layer Hardening Stack

### Layer 1: Dedicated Unprivileged System User
During server bootstrapping, Anode ensures the `anode` user exists:
```bash
id -u anode &>/dev/null || useradd -r -s /bin/false anode
```
All compiled microservices execute strictly as `User=anode`.

### Layer 2: Deterministic POSIX Directory Permissions
Database persistent directories at `/var/lib/anode/data/<resource>` are initialized using the specific UID/GID required by the database engine:
```bash
install -d -m 0700 -o 999 -g 999 /var/lib/anode/data/orders-db
```
Other users and applications on the server cannot read or write to this directory.

### Layer 3: Systemd Service Sandboxing
Every microservice unit generated by Anode incorporates kernel security directives:
```systemd
[Service]
User=anode
WorkingDirectory=/var/lib/anode/releases/<release_id>
ExecStart=/var/lib/anode/releases/<release_id>/orders

# Least-Privilege Sandboxing
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectControlGroups=true
RestrictSUIDSGID=true
ReadWritePaths=/var/lib/anode/releases/<release_id>

# Cgroups v2 Resource Governance
MemoryMax=1G
CPUQuota=200%
```

### Layer 4: Kernel OOM Score Priority Tiering
The Linux kernel uses `oom_score_adj` to determine process kill order under memory pressure:
- **Stateful Databases (`-900`)**: Immune from kernel termination.
- **Message Brokers & Caches (`-500`)**: High survival priority.
- **Microservices (`+500`)**: Sacrificed first. Systemd restarts the killed microservice cleanly without corrupting the database.

### Layer 5: Strict Network Loopback Isolation
Stateful dependency containers bind exclusively to `127.0.0.1` via `-p 127.0.0.1:<port>:<port>`. They are physically unreachable from the public internet interface.

### Layer 6: Modern TLS Edge Termination
Caddy terminates traffic at the public edge with automatic Let's Encrypt certificates, TLS 1.3, and HTTP/2 + HTTP/3 support.
